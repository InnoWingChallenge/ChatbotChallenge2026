# 图片证据整理：输入快照

用户已确认筛选模型为 **gpt-6-luna / low（light）**。
三名该模型子代理分别处理 `packet-0/1/2.json`，记录于 `review_run.json`。
可入库交付文件位于 `release/`；只有导出成功并生成 `report.json` 才算交付完成。

从 `submission_repo` 运行 `python -m build.prepare_image_curation` 可重新准备：

- `inputs.json`：已完成且来源哈希通过校验的描述、原图路径、原始上下文，以及按来源 URL 精确关联的网页正文。
- `baseline_records.json`：原有图片证据的比较快照；其中的模型描述并不自动具有事实优先权。
- `inventory.json`：输入覆盖范围、缺失任务、来源哈希和模型分布。

准备阶段不按 suitable 删除图片，不做语义筛选，不调用 API，不修改数据库。
缺失描述不计作无价值；未匹配正文不等于没有网页上下文。

## 整理约定

每条入选事实须追溯到原始描述字段或网页原文，保留来源路径、图像哈希、
描述模型、整理模型及版本。图片观察与网页说法分别标记；网页标题不能直接证明
拍摄地点，产品图不能证明场地拥有该设备，旧描述不能自动解决新旧证据冲突。
未经原图核查的事实不得标记为视觉核验通过。

筛选结果分别记录保留、去重、无关、证据不足和冲突，不丢弃原始描述。
不确定的型号、数量、地点归属以及相互冲突的说法进入待核查清单。
相似度检索只产生比较候选，不能据此确定两个设备是同一实体。

目标交付：

1. `records.json`：与现有 make_record 格式兼容的可入库片段。
2. `sources.json`：图片、网页及原始描述的溯源信息。
3. `decisions.json`：逐图、逐事实的筛选理由及关联证据。
4. `needs_review.json`：不进入正式数据的冲突与待核查项。
5. `report.json`：覆盖率、保留/排除数量、模型、校验结果和交付文件哈希。

另有 `merged_records.json` 和 `merged_sources.json`，在当前原有图片证据及
来源清单上追加本次片段。
`records.json` 仅包含新增片段，**不要单独交给现有 `index_chroma`**：
现有函数会清理同一 pipeline 下未出现的旧记录。入库时应使用经过确认的
合并集合，并确保原有证据在本次快照后未改变；不能直接覆盖正在使用的文件。

交付前须校验 ID 唯一性、来源引用和哈希、
模型标记、原始字段引用、证据类型、重复片段及所有输入的处理覆盖情况。
最终数据仅准备供后续入库，不自动执行 embedding 或修改 Chroma。

## 重建与质量边界

在 `submission_repo` 运行 `python -m build.export_curated_images`。
它只使用已保存的子代理决定，不调用模型；输入变化会使校验失败，需要重新核查。
不要在已开始筛选后重跑输入准备来覆盖快照。

保留的句子按字段和零起始索引精确引用原描述，不生成额外设备规格。
为避免未经核查的标题带入断言，检索片段标题使用通用设备/空间分类，
设备名称应出现在被保留的句子或 OCR 内。原始描述模型、prompt 版本、
整理模型、原图路径、网页上下文和被移除信息的理由分别保留。

这是**文字层筛选**，没有逐图重新视觉核验。所有新片段使用
`status=text_curated_not_visual_verified`、`location=unknown`，
不得把旧网页标题、拍摄数量或产品照片推导为当前场地库存。
网页正文按来源 URL 精确关联；旧图片证据通过词项相似度提供三个比较候选，
并非完整语义检索，所以跨视角或不同措辞的重复仍可能存在。
对较长网页，子代理按相关上下文选择阅读，没有保证全文逐行核查；
因此本轮不能视为穷尽的事实核验或冲突检测，也尚未验证 RAG 准确率提升。
缺少描述的图片列在 `inventory.json` 中，不混入本次交付。
